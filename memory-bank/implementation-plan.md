# 铁道运转记录程序 (Train Ledger) - 开发阶段规划

## 技术决策速查

| 决策项 | 结论 |
|--------|------|
| 状态管理 | Riverpod |
| 级联选择器风格 | CupertinoPicker（iOS 拨轮），应用整体严格遵循 Material You |
| Android SDK | minSdkVersion: 21 / targetSdkVersion: 34 / compileSdkVersion: 34 |
| CSV 编码 | UTF-8 with BOM |
| 海报分享 | MVP 预留入口和开发空间，择机开发升级 |

---

## 第一阶段：项目地基与静态字典

**目标**：建立项目骨架，准备好专业记录所需的底座数据。

### 第 1 步：Flutter 环境初始化

- 操作：
  - 创建 Flutter 项目，清理默认代码。
  - 配置 Android SDK 版本：minSdkVersion 21、targetSdkVersion 34、compileSdkVersion 34。
  - 引入核心依赖：`flutter_riverpod`、`isar`、`isar_flutter_libs`、`freezed`、`json_serializable`、`flex_color_scheme`、Material Icons。
  - 建立项目目录结构（lib/ 下按 feature 分层：models / providers / pages / widgets / utils / data）。
- 验证测试：应用在安卓模拟器或真机上成功运行，显示一个简单的"Hello Ledger"页面。

### 第 2 步：构建铁路字典 (JSON)

- 操作：手工编写以下 JSON 文件：

  **train_hierarchy.json（车型级联数据）**

  L1 大类共 6 个，每个 L1 条目包含 `type` 标识符区分车辆性质：

  | L1 代码 | 名称 | type 标识 | 说明 |
  |---------|------|-----------|------|
  | CR | 复兴号系列 | EMU | 目前主力，分类极细 |
  | CRH | 和谐号系列 | EMU | 早期 1/2/3/5/6 及 380 系列 |
  | HXD | 和谐型电力机车 | Loco | 普速列车牵引 |
  | SS | 韶山系列机车 | Loco | 怀旧与普速主力 |
  | DF/HXN | 内燃机车系列 | Loco | 非电化区间 |
  | Coach | 普速客车车底 | Coach | 25T/25G 等 |

  MVP 必须完整覆盖的数据（覆盖 90% 运转场景）：
  - CR 全部平台：400AF 系列、400BF 系列、300 系列、200J（绿巨人）
  - CRH 主流平台：1A, 2A, 3C, 5A, 380A/AL, 380B/BL, 380CL, 380D, 6A
  - 主流普速机车：HXD1D, HXD3D, SS8, SS9, DF4B, DF11G
  - 主流普速车底：25T (DC600V), 25G, 25K

  JSON 结构示例：
  ```json
  {
    "CR": {
      "label": "复兴号系列",
      "type": "EMU",
      "platforms": {
        "CR400AF": {
          "label": "CR400AF系列",
          "versions": ["CR400AF", "CR400AF-A", "CR400AF-B", "CR400AF-Z", "CR400AF-AZ", "CR400AF-BZ", "CR400AF-C"]
        }
      }
    }
  }
  ```

  **railway_bureau.json（18 局字典，两层结构）**

  - 第一级：18 个铁路局（如京局、沪局、广铁等）
  - 第二级：各局下属的段，每个段带 `category` 字段标识类型（客运/机务等）
  - 级联选择器第二级默认只显示 `category == "客运"` 的段
  - 除非用户在设置中开启了"机务记录模式"，才显示机务类型的段
  - 选择器末尾提供"其他"选项，允许手动录入不在字典中的段

  JSON 结构示例：
  ```json
  {
    "京局": {
      "sections": [
        {"name": "京段", "category": "客运"},
        {"name": "津段", "category": "客运"},
        {"name": "京机", "category": "机务"}
      ]
    }
  }
  ```

- 验证测试：编写一个简单的脚本或在控制台打印解析结果，确认能通过"CR"索引到"CR400AF-Z"，确认段数据能按 category 过滤。

## 第二阶段：核心记录表单 (录入端)

**目标**：完成那个"极其专业"的 12+ 字段录入界面。

### 第 3 步：三级级联选择器 UI

- 操作：
  - 实现车型选择逻辑（L1→L2→L3），使用 CupertinoPicker（iOS 拨轮风格）。
  - 三个拨轮联动：选择 L1 后，L2 拨轮的选项自动更新；选择 L2 后，L3 拨轮的选项自动更新。
  - 选择器以 BottomSheet 形式弹出，整体应用严格遵循 Material You 设计规范。
  - 乘务担当（局→段）同样使用 CupertinoPicker 二级联动，第二级默认过滤只显示客运段。
- 验证测试：手动操作选择器，确认选定 CR 后，下一级不会出现 HXD 的平台；确认客运模式下不显示机务段。

### 第 4 步：全字段表单布局

- 操作：排布所有输入字段，共 12+ 个：

  | 字段 | 输入方式 | 说明 |
  |------|----------|------|
  | 车次 | 手动输入 | 如 G1 |
  | 运转区间-乘车站 | 手动输入 | 乘客实际上车站 |
  | 运转区间-到达站 | 手动输入 | 乘客实际下车站 |
  | 始发终到-始发站 | 手动输入 | 该车次全程起点站 |
  | 始发终到-终到站 | 手动输入 | 该车次全程终点站 |
  | 运转时间 | DateTime Picker | 精确到分钟的出发时间 |
  | 票价 | 数字输入 | 货币金额 |
  | 乘务担当 | CupertinoPicker 二级联动 | 局→段，默认过滤客运段 |
  | 车次类型 | 自动识别 | 根据车次首字母：G/D/C/Z/T/K 等 |
  | 席位-类别 | 一级下拉 | 选项：坐席 / 卧席 |
  | 席位-类型 | 二级下拉（自动过滤） | 选坐席→显示无座/硬座/软座/二等座/一等座/商务座；选卧席→显示硬卧/软卧/二等卧/一等卧/高级软卧 |
  | 车底型号 | CupertinoPicker 三级联动 | L1→L2→L3 |
  | 备注 | 多行文本输入 | 自由文本 |

- 验证测试：在界面上填完所有 12 个字段，确认 UI 布局在不同屏幕尺寸下没有遮挡；确认席位二级联动正确过滤。

## 第三阶段：本地存储引擎 (数据端)

**目标**：让你的记录能存得下来，关掉 App 也不丢失。

### 第 5 步：Isar 数据库集成

- 操作：
  - 配置 Isar 数据模型（Trip 类），字段与表单一一对应。
  - Trip 模型中 `operator` 字段需支持"其他"手动录入的情况（存储为自由字符串）。
  - `train_model` 字段存储三级结构（category/platform/version）。
  - `seat` 字段存储二级结构（category/type）。
  - 建立数据库连接，配置 Riverpod Provider 提供数据库实例。
- 验证测试：点击"保存"后，在控制台查看数据库路径下是否生成了数据文件，并能查询出刚才存入的记录。

### 第 6 步：数据存取流程闭环

- 操作：
  - 实现"保存-读取-编辑-删除"完整 CRUD 逻辑。
  - 编辑功能：从历史记录点击进入录入页，预填充已有数据，保存时更新而非新建。
  - 使用 Riverpod 的 AsyncNotifierProvider 管理数据状态，确保 UI 自动响应数据变化。
- 验证测试：保存一条记录，彻底杀死 App 进程并重启，确认刚才录入的信息能被重新读取出来；编辑一条记录，确认修改后数据正确更新。

## 第四阶段：首页总结与列表 (展示端)

**目标**：实现"仪表盘+历史记录"的核心展示逻辑。

### 第 7 步：全屏仪表盘 Dashboard

- 操作：计算数据库内所有记录的核心统计指标，以大字号展示在首页顶部：
  - **年运转次数**（当前年份的运转次数）
  - **总花费金额**（所有记录的票价累计，单位：元）
  - **已运转车底数量**（去重统计不同车底型号的数量）
  - 仪表盘采用可扩展卡片式布局，预留后续新增统计维度的开发空间（如总运转里程、最常乘坐路线、年度花费趋势等）。
- 验证测试：新增一条记录，回到首页看仪表盘数字是否即时更新。

### 第 8 步：历史记录流与筛选

- 操作：
  - 实现下滑展示记录卡片，卡片内容：车次、日期、区间、车型、席位。
  - 加入顶部筛选按钮，支持以下筛选维度：
    - **年份**
    - **车次等级**（G/D/C/Z/T/K 等）
    - **局段**
  - 筛选条件可组合使用。
- 验证测试：在有 10 条不同年份、不同车次等级记录的情况下，点击筛选"2023"和"G"，列表应只显示 2023 年 G 字头的数据。

## 第五阶段：成就感与图库 (激励端)

**目标**：让记录变有趣，像集邮一样收集车型。

### 第 9 步：车型照片映射系统

- 操作：将 assets 文件夹中的图片与数据库字段关联。实现逻辑：若 model_id.jpg 存在则显示，否则显示 silhouette.png。
- 验证测试：录入一条有照片的车型（如 CR400AF）和一条无照片的车型（如 K 字头），确认卡片展示正确。

### 第 10 步：成就统计页面

- 操作：在 Dock 栏第二页实现：
  - **收集者 (Collector)**：统计车底型号的覆盖率，展示已解锁车型的图标。有照片显示照片，无照片显示通用剪影。展示收集率进度条（已解锁型号 / 总型号）。
  - **领航者 (Navigator)**：统计运转次数勋章，等级如下：
    - 1 次 / 10 次 / 50 次 / 100 次 / 200 次 / 500 次 / 1,000 次 / 5,000 次
    - 不设置等级名称，仅显示次数
  - 预留扩展：后续引入里程字段后，可新增里程勋章（100 km / 500 km / 1,000 km / 5,000 km / 10,000 km / 50,000 km / 100,000 km），与运转次数勋章并列展示。
- 验证测试：检查进度条百分比是否计算正确；检查运转次数勋章解锁逻辑是否与总次数匹配。

## 第六阶段：数据导出与分享 (工具端)

**目标**：打通数据孤岛，让专业记录可以流转。

### 第 11 步：CSV 导出功能

- 操作：
  - 将数据库中的所有 Trip 对象转换为文本字符串，保存为 .csv 文件至系统下载文件夹。
  - 编码必须使用 **UTF-8 with BOM**，确保中文环境下 Excel 打开不乱码。
- 验证测试：在安卓文件管理器中找到生成的 CSV，用 Excel 或 WPS 打开，确认表头和数据无误，中文显示正常。

### 第 12 步：海报分享功能（预留）

- 操作：
  - 在记录详情页预留"分享"按钮入口。
  - 定义海报数据接口（接收单个 Trip 对象 + 车型图片），预留 Canvas 渲染的开发空间。
  - MVP 阶段点击按钮提示"功能开发中"，择机开发升级。
- 验证测试：点击分享按钮，确认入口可见且提示信息正确显示。
